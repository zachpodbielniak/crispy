* Crispy Architecture
:PROPERTIES:
:CUSTOM_ID: crispy-architecture
:END:
** Overview
:PROPERTIES:
:CUSTOM_ID: overview
:END:
Crispy is structured as a GObject library (=libcrispy=) with a thin CLI frontend. The library is built around two GInterfaces that define the compilation and caching contracts, making it easy to extend with custom backends.

                    ┌──────────────────┐
                    │    main.c (CLI)   │
                    └────────┬─────────┘
                             │ uses
                    ┌────────▼─────────┐
                    │  CrispyScript     │ (Final type - orchestrator)
                    │                   │
                    │  - source parsing │
                    │  - pipeline exec  │
                    │  - GModule load   │
                    │  - plugin hooks   │
                    └──┬──────┬────┬───┘
                       │      │    │
              uses     │      │    │ optional
          ┌────────────▼──┐   │   ┌▼─────────────────┐
          │ CrispyCompiler │   │   │ CrispyPluginEngine│
          │  (GInterface)  │   │   │ (Final type)      │

*** Interfaces
:PROPERTIES:
:CUSTOM_ID: interfaces
:END:
Interfaces define contracts that concrete types implement. They are the primary extension points.

**** CrispyCompiler
:PROPERTIES:
:CUSTOM_ID: crispycompiler
:END:
Defined in =src/interfaces/crispy-compiler.h=.

The compilation contract. Any type implementing this interface can serve as a compilation backend.

*Virtual methods:*

| Method                 | Description                                           |
|------------------------+-------------------------------------------------------|
| =get_version()=        | Returns compiler version string (cache key component) |
| =get_base_flags()=     | Returns default pkg-config flags for GLib libraries   |
| =compile_shared()=     | Compiles source to a =.so= for dynamic loading        |
| =compile_executable()= | Compiles source to an executable with debug symbols   |

*Implementing a custom compiler backend:*

To add support for a different compiler (e.g., clang, tcc), create a new GObject final type that implements =CrispyCompiler=:

#+begin_src C
/* crispy-clang-compiler.h */
G_DECLARE_FINAL_TYPE(CrispyClangCompiler, crispy_clang_compiler,
                     CRISPY, CLANG_COMPILER, GObject)

CrispyClangCompiler *crispy_clang_compiler_new(GError **error);
#+end_src

#+begin_src C
/* crispy-clang-compiler.c */
struct _CrispyClangCompiler
{
    GObject parent_instance;
};

typedef struct
{
    gchar *clang_version;
    gchar *base_flags;
} CrispyClangCompilerPrivate;

static void
compiler_iface_init(CrispyCompilerInterface *iface)
{
    iface->get_version = clang_get_version;
    iface->get_base_flags = clang_get_base_flags;
    iface->compile_shared = clang_compile_shared;
    iface->compile_executable = clang_compile_executable;
}

G_DEFINE_FINAL_TYPE_WITH_CODE(CrispyClangCompiler,
    crispy_clang_compiler, G_TYPE_OBJECT,
    G_ADD_PRIVATE(CrispyClangCompiler)
    G_IMPLEMENT_INTERFACE(CRISPY_TYPE_COMPILER, compiler_iface_init))
#+end_src

Then pass it to =CrispyScript= like any other compiler:

#+begin_src C
g_autoptr(CrispyClangCompiler) compiler = crispy_clang_compiler_new(&error);
script = crispy_script_new_from_file(path,
    CRISPY_COMPILER(compiler), cache, flags, &error);
#+end_src

**** CrispyCacheProvider
:PROPERTIES:
:CUSTOM_ID: crispycacheprovider
:END:
Defined in =src/interfaces/crispy-cache-provider.h=.

The caching contract. Any type implementing this interface can serve as a cache backend.

*Virtual methods:*

| Method           | Description                                            |
|------------------+--------------------------------------------------------|
| =compute_hash()= | Computes SHA256 from source + flags + compiler version |
| =get_path()=     | Returns the filesystem path for a cached artifact      |
| =has_valid()=    | Checks if a valid (non-stale) cache entry exists       |
| =purge()=        | Removes all cached artifacts                           |

*Implementing a custom cache backend:*

For example, an in-memory cache for testing or short-lived processes:

#+begin_src C
G_DECLARE_FINAL_TYPE(CrispyMemoryCache, crispy_memory_cache,
                     CRISPY, MEMORY_CACHE, GObject)
#+end_src

Or a network-shared cache using a key-value store. The interface makes no assumptions about the storage mechanism -- only that it can hash, store, check, and purge.

*** Concrete Types
:PROPERTIES:
:CUSTOM_ID: concrete-types
:END:
**** CrispyGccCompiler
:PROPERTIES:
:CUSTOM_ID: crispygcccompiler
:END:
Defined in =src/core/crispy-gcc-compiler.h/.c=. Implements =CrispyCompiler=.

On construction, probes the system for:

- gcc binary location and version (=gcc --version=)
- Base pkg-config flags (=pkg-config --cflags --libs glib-2.0 gobject-2.0 gio-2.0 gmodule-2.0=)

Compilation commands:

- *Shared object*: =gcc -std=gnu89 -shared -fPIC <base_flags> <extra_flags> -o <output> <source>=
- *Executable*: =gcc -std=gnu89 -g -O0 <base_flags> <extra_flags> -o <output> <source>=

All process spawning uses =g_spawn_command_line_sync()=. Compilation errors include gcc's stderr in the GError message.

**** CrispyFileCache
:PROPERTIES:
:CUSTOM_ID: crispyfilecache
:END:
Defined in =src/core/crispy-file-cache.h/.c=. Implements =CrispyCacheProvider=.

- Cache directory: =~/.cache/crispy/= (via =g_get_user_cache_dir()=)
- Hash algorithm: SHA256 via =GChecksum=
- Hash inputs: source content + NUL + extra_flags + NUL + compiler_version
- Cached artifacts: =~/.cache/crispy/<sha256hex>.so=, with the header list beside it as =<sha256hex>.d=
- Purge: iterates the directory and removes =*.so=, =*.d= and any =.crispy-stage-*= a killed compile left behind

An entry is a cache hit only when all of these hold:

1. It is a *complete ELF shared object*. Existence alone is not enough: a compile that was killed, or one read while the linker was still writing, leaves a regular file newer than the script that =g_module_open()= rejects with "file too short". Before this check such an entry was a hit for ever and only =--no-cache= got past it.
2. Its mtime is no older than the script's, when a script path is known.
3. Every header listed in its =.d= dependency file is older than the entry. The hash covers the script text, the flags and the compiler version, and none of them changes when a header the script includes is edited -- so without this an edited header gave back the previous build, silently. The dependency file is written by the compiler backend (=gcc -MMD -MF=); an entry with no =.d= beside it is treated as fresh, which is how a backend that records nothing keeps working.

*** Publishing a compiled artifact
:PROPERTIES:
:CUSTOM_ID: publishing-a-compiled-artifact
:END:
=crispy_compiler_compile_shared()= and =crispy_compiler_compile_executable()= do not hand the caller's output path to the backend. They create a staging name in that path's own directory, compile into it, and =rename()= the result into place -- atomically, since the two names share a filesystem.

The cache path is what other processes load from. Handing it to gcc directly meant that a concurrent run could =g_module_open()= a file the linker had not finished: eight concurrent runs of one script against a cold cache failed in four of six rounds with "file too short" and "invalid ELF header". A failed or interrupted compile now leaves the previous entry untouched rather than replacing it with a stub.

A dependency file the backend wrote beside the staged object is renamed with it, and before it, so an artifact never becomes visible without its header list.

**** CrispyPluginEngine
:PROPERTIES:
:CUSTOM_ID: crispypluginengine
:END:
Defined in =src/core/crispy-plugin-engine.h/.c=. Final type -- not an interface.

Manages the lifecycle of Crispy plugins. Plugins are =.so= files loaded via GModule that export well-known C symbols. The engine resolves these symbols at load time and dispatches hook calls during script execution.

Every plugin exports the same set of names -- =crispy_plugin_info= is the
ABI and cannot be made unique -- so they are opened with
=G_MODULE_BIND_LOCAL=. Opened globally, two plugins put two definitions
of each of those names into one process, and the second plugin's own
references bind to the first plugin's copy; the same global scope is
what a script's compiled module is loaded into. AddressSanitizer reports
the pair as an =odr-violation= and aborts, which is what =make DEBUG=1
ASAN=1 test= did. Nothing looks a plugin's symbols up by global name:
they are reached with =g_module_symbol()= on the handle that loaded
them, which searches that object either way.

*Key features:*

- Load plugins from paths (single or colon/comma-separated list)
- Resolve mandatory =crispy_plugin_info= and optional hook/lifecycle symbols
- Open each =.so= with =G_MODULE_BIND_LOCAL=, so its symbols reach the
  engine's own handle and nothing else
- Dispatch hooks at 9 pipeline phases
- Shared data store for inter-plugin communication
- Plugin init/shutdown lifecycle management

*Public API:*

| Method                                    | Description                            |
|-------------------------------------------+----------------------------------------|
| =crispy_plugin_engine_new()=              | Create empty engine                    |
| =crispy_plugin_engine_load()=             | Load a single plugin .so               |
| =crispy_plugin_engine_load_paths()=       | Load colon/comma-separated plugin list |
| =crispy_plugin_engine_get_plugin_count()= | Number of loaded plugins               |
| =crispy_plugin_engine_set_data()=         | Store data in shared store             |
| =crispy_plugin_engine_get_data()=         | Retrieve data from shared store        |

See [[file:plugins.org][docs/plugins.md]] for plugin authoring guide.

**** CrispyScript
:PROPERTIES:
:CUSTOM_ID: crispyscript
:END:
Defined in =src/core/crispy-script.h/.c=. Final type -- not an interface.

The orchestrator that ties everything together. It takes a =CrispyCompiler= and =CrispyCacheProvider= via its constructors, making it fully decoupled from specific implementations.

*Construction modes:*

- =new_from_file()= -- reads source from a file path
- =new_from_inline()= -- wraps inline code in a main() function
- =new_from_stdin()= -- reads source from stdin, wraps in main()

*Execution pipeline:*

See the Execution Pipeline section below.

** Execution Pipeline
:PROPERTIES:
:CUSTOM_ID: execution-pipeline
:END:
#+begin_example
Source (file / -i / stdin)
  │
  ▼
[1] Read source content
  │
  ▼
[2] Strip shebang (if line 1 starts with #!)
  │
  ▼
[3] Parse & extract #define CRISPY_PARAMS "..."
  │  (remove that line from modified source)
  │
  ▼                                          ┌─────────────────────┐
  ├──► HOOK: SOURCE_LOADED          ◄────────┤ Plugins can modify  │
  │                                          │ source, abort       │
  ▼                                          └─────────────────────┘
[4] Shell-expand CRISPY_PARAMS via /bin/sh -c "printf '%s' <params>"
  │
  ├──► HOOK: PARAMS_EXPANDED
  │
  ▼
[5] Compute SHA256(modified_source + expanded_params + compiler_version)
  │
  ├──► HOOK: HASH_COMPUTED
  │
  ▼
[6] Check cache ──[HIT]──► skip to [9]
  │                                          ┌─────────────────────┐
  ├──► HOOK: CACHE_CHECKED          ◄────────┤ Plugins can force   │
  │                                          │ recompilation       │
 [MISS]                                      └─────────────────────┘
  │
  ▼
[7] Write modified source to /tmp/crispy-XXXXXX.c
  │                                          ┌─────────────────────┐
  ├──► HOOK: PRE_COMPILE            ◄────────┤ Plugins can inject  │
  │                                          │ compiler flags      │
  ▼                                          └─────────────────────┘
[8] Compile:
  │  Normal: compile_shared() → ~/.cache/crispy/<hash>.so
  │  GDB:    compile_executable() → /tmp/crispy-dbg-XXXXXX
  │
  ├──► HOOK: POST_COMPILE
  │
  ▼
[9] g_module_open(cached_so_path, G_MODULE_BIND_LAZY)
  │  (GDB mode: execvp("gdb", "--args", executable, ...) instead)
  │
  ├──► HOOK: MODULE_LOADED
  │
  ▼
[10] g_module_symbol(module, "main") → CrispyMainFunc pointer
  │                                          ┌─────────────────────┐
  ├──► HOOK: PRE_EXECUTE            ◄────────┤ Plugins can modify  │
  │                                          │ argc/argv           │
  ▼                                          └─────────────────────┘
[11] main_func(argc, argv)
  │
  ├──► HOOK: POST_EXECUTE
  │
  ▼
[12] Cleanup: g_module_close(), unlink temp (unless -S)
  │
  ▼
Exit with script's return code
#+end_example

=--dry-run= stops the pipeline immediately after step [6], whichever way
the cache went, and prints what would have happened: =Would compile:
<temp source> -> <cache path>= on a miss, =Would load: <cache path>= on a
hit.  It used to be tested inside the =[MISS]= arm, so a warm cache --
every run of a script after the first -- fell through to step [9] and
executed it.  The answer to "does this run the script?" does not depend
on the cache, so the test cannot live on one side of that branch; only
the sentence printed does, which is why it comes after the lookup rather
than before it.

When plugins are loaded via =--plugins=/=-P=, each hook dispatches to all loaded plugins in order. If any plugin returns =CRISPY_HOOK_ABORT=, the pipeline stops immediately. All timing data is accumulated and available to post-execute hooks.

** Configuration System
:PROPERTIES:
:CUSTOM_ID: configuration-system
:END:
Crispy supports a C-based configuration file that is compiled and loaded using crispy's own compilation and caching infrastructure. The config system operates independently of =CrispyScript= -- it does not trigger plugin hooks during its own compilation.

*** Components
:PROPERTIES:
:CUSTOM_ID: components
:END:
| Component             | File                                        | Description                                        |
|-----------------------+---------------------------------------------+----------------------------------------------------|
| =CrispyConfigContext= | =src/core/crispy-config-context.h/.c=       | Plain struct (not GObject) with setter/getter API  |
| Config Loader         | =src/core/crispy-config-loader.h/.c=        | Internal: finds, compiles, loads, and calls config |
| Source Utilities      | =src/core/crispy-source-utils-private.h/.c= | Shared: CRISPY_PARAMS extraction, shell expansion  |

*** Design Decisions
:PROPERTIES:
:CUSTOM_ID: design-decisions
:END:
- *Plain struct, not GObject* -- =CrispyConfigContext= is short-lived (stack-allocated in main.c), needs no signals/properties, follows the =CrispyHookContext= pattern.
- *Direct interface usage* -- The config loader uses =CrispyCompiler= and =CrispyCacheProvider= interfaces directly, not =CrispyScript=, since config files have a =crispy_config_init()= entry point (not =main()=) and should not trigger plugin hooks.
- *Config loads before plugins* -- The config can specify which plugins to load, so it must run first.
- *CLI overrides config* -- If both config and CLI set flags, they are OR'd together (CLI always wins).
- *Config .so stays loaded* -- The compiled module is kept open so config symbols remain available.
- *Opaque struct* -- The struct definition is only visible to internal code (=CRISPY_COMPILATION=); config authors use the setter/getter API.

*** Compiler Flag Hierarchy
:PROPERTIES:
:CUSTOM_ID: compiler-flag-hierarchy
:END:
#+begin_example
┌──────────────────────────────────────────────────────────────────────┐
│                  Final gcc command line (left to right)              │
├────────────┬──────────┬──────────────┬──────────────┬───────────────┤
│ script dir │ extra_   │ CRISPY_      │ plugin       │ override_     │
│ + CRISPY_  │ flags    │ PARAMS       │ extra_flags  │ flags         │
│ USE        │          │              │              │               │
│ (what the  │ (config  │ (per-script) │ (PRE_COMPILE │ (config forced│
│ script     │ defaults)│              │  hook)       │  overrides)   │
│ needs at   │          │              │              │               │
│ all)       │ LOWEST   │              │              │ HIGHEST       │
└────────────┴──────────┴──────────────┴──────────────┴───────────────┘
                    gcc last-wins semantics
#+end_example

Tier 0 is built by =build_compile_flags()= in =crispy-script.c= and covers the two things that decide how a script compiles but are written nowhere in =CRISPY_PARAMS=:

- =-I<the script's own directory>=, because compilation happens on a stripped copy in the temp directory. Without it =#include "sibling.h"= could not resolve on the path that runs a script, while =crispy lint= -- which compiled the file in place -- reported the script clean. =lint= now works from a copy too, for the shebang's sake, and so it adds the same flag.
- the flags resolved from =#define CRISPY_USE=. =lint=, =test= and =install= each resolved it and the runner did not, so a script that linted clean failed to compile on the header it had already declared.

One function builds this for both compiles crispy performs: the ordinary shared object and the executable that =--gdb= and =--profile= need.

*** Temp files and signals
:PROPERTIES:
:CUSTOM_ID: temp-files-and-signals
:END:
Three places write a C file into =g_get_tmp_dir()= and remove it when they are done: =CrispyScript= (the stripped source), =CrispyRepl= (one per evaluation) and the test runner (its harness). Each registers its path with =crispy_temp_registry_add()= the moment the file exists, and the CLI installs =sigaction()= handlers that empty the registry and then let the signal kill the process.

Two things made this necessary:

- =g_unix_signal_add()= puts the handler on a GLib source, which runs only while something iterates the main context it was attached to. A crispy run has no main loop outside =--watch=, so SIGINT and SIGTERM were caught and never dispatched -- the process carried on with the signal bits set in =SigCgt= and nothing else happened.
- The CLI captured the script's temp source path *before* =crispy_script_execute()= created the file, so its cleanup was always holding =NULL=.

The registry is a fixed table read with atomic loads and emptied with =unlink()=, because a signal handler can neither take a lock nor wait on an allocator.

** Internal Components
:PROPERTIES:
:CUSTOM_ID: internal-components
:END:
Beyond the public types, the library carries a set of =-private.c= /
=-private.h= modules. These are compiled into =libcrispy.so= but their
headers are *not installed* and not reachable through =crispy.h=. They
are documented here because they explain how the pipeline and the
subcommands actually work -- not because they are API. Anything here may
change shape between releases.

| Module                | Responsibility                                                        |
|-----------------------+-----------------------------------------------------------------------|
| =source-utils=        | Extracts =CRISPY_PARAMS=, shell-expands it, strips the crispy header   |
| =shebang-parser=      | Finds the shebang line and its interpreter and arguments              |
| =use-parser=          | Parses =CRISPY_USE=, splits the package list, resolves it to flags     |
| =header-tracker=      | Reads the =.d= depfile; decides whether a tracked header went stale    |
| =temp-registry=       | Async-signal-safe table of temp files to unlink on SIGINT/SIGTERM      |
| =error-analyzer=      | Reads a failed compile's stderr and suggests the pkg-config package    |
| =profiler=            | Supplies =-pg=, runs =gprof=, cleans up =gmon.out= (=--profile=)       |
| =scaffolder=          | The built-in templates behind =crispy new=                            |
| =linter=              | Strict-warning =-fsyntax-only= pass over a header-blanked copy         |
| =installer=           | Compiles to a native binary and installs it (=crispy install=)        |
| =test-runner=         | Discovers =test_*()=, generates a GTest harness (=crispy test=)       |
| =config-loader=       | Finds, compiles, and loads =config.c=; resolves =crispy_config_init=  |
| =plugin-engine-private= | The internal hook dispatch entry point                              |

*** Why these are private
:PROPERTIES:
:CUSTOM_ID: why-private
:END:
The three GInterfaces are the extension points, and each one is a
contract someone could plausibly reimplement: a different compiler, a
different cache, a different dependency resolver. The modules above are
not contracts -- they are one implementation of one behaviour, and
freezing them as public API would mean promising that =crispy new= keeps
exactly four templates, or that staleness keeps being judged from a gcc
=.d= file. Keeping them private is what lets those change.

The dividing line is deliberate: *if a reasonable person might want to
swap it out, it is an interface; if they would only ever want to use it,
it is private.*

*** Three things worth knowing about them
:PROPERTIES:
:CUSTOM_ID: private-notes
:END:
The *error analyzer* runs only on the failure path. When a compile fails
it scans stderr for =fatal error: foo/foo.h: No such file or directory=
and maps the header back to the pkg-config package that provides it, so
the message a user gets names the =CRISPY_USE= line they should have
written rather than only the header they were missing.

The *linter* cannot hand gcc the script, because a shebang is not a
preprocessing directive and gcc rejects the file on line 1. It compiles a
copy instead, and two details keep the diagnostics honest: the header
lines are *blanked rather than deleted*, so nothing after them shifts,
and the copy opens with a =#line= directive naming the original file, so
gcc reports the script's own path and reads its source context from it.
Deleting the lines, the way the run path does, would silently renumber
every diagnostic -- which for a tool whose entire output is line numbers
is worse than the bug it fixes.

The *header tracker* is why the cache is not simply "artifact newer than
script". gcc is asked for a depfile, which is published alongside the
=.so= as =<hash>.d=; on the next run every header listed there is checked
against the artifact's mtime. Editing a header a script includes
invalidates the entry even though the script itself did not change.

** Extensibility
:PROPERTIES:
:CUSTOM_ID: extensibility
:END:
There are three ways to extend crispy, in increasing order of
commitment.

*** 1. Config file
:PROPERTIES:
:CUSTOM_ID: extend-config
:END:
=~/.config/crispy/config.c= is itself a C file that crispy compiles and
loads, and its =crispy_config_init()= receives a =CrispyConfigContext=.
That is enough to set default flags, force overrides, pick a cache
directory, load plugins, and rewrite argv -- no rebuild of crispy
required. See [[file:config.org][Configuration]].

*** 2. Plugin
:PROPERTIES:
:CUSTOM_ID: extend-plugin
:END:
A plugin is a =.so= exporting hook functions, loaded via =-P= or from
the config file, and dispatched at nine points across the pipeline. A
hook can read the source, rewrite it, add compiler flags, force a
recompile, or abort the run. This is the right level for policy --
source auditing, timing, flag injection -- because it needs no changes
to crispy and no reimplementation of anything. See
[[file:plugins.org][the Plugin Authoring Guide]].

*** 3. Interface implementation
:PROPERTIES:
:CUSTOM_ID: extend-interface
:END:
Implementing =CrispyCompiler=, =CrispyCacheProvider=, or
=CrispyDependencyResolver= replaces a whole backend. =CrispyScript=
takes its compiler and cache as constructor arguments and calls them
only through the vfuncs, so a replacement needs no changes anywhere else
in the library.

| Interface                  | Implement it to get                                          |
|----------------------------+--------------------------------------------------------------|
| =CrispyCompiler=           | clang, tcc, a remote build service, a compile-server client   |
| =CrispyCacheProvider=      | an in-memory cache, a shared network cache, a content store   |
| =CrispyDependencyResolver= | resolution from a lockfile, a vendored manifest, or a sysroot |

This path is for the library consumer, not the CLI user: the =crispy=
executable always constructs =CrispyGccCompiler= and =CrispyFileCache=.
Selecting implementations from the CLI is not currently possible.

*** What a replacement backend must honour
:PROPERTIES:
:CUSTOM_ID: backend-contract
:END:
The vfunc signatures are not the whole contract. Two invariants live in
the prose rather than the types, and a backend that ignores them will
appear to work and then corrupt a concurrent run:

- *Compilation must publish atomically.* Write to a staging name in the
  output's own directory and rename it into place, so a reader sees
  either the previous artifact or the complete new one. A failed compile
  must leave the output path untouched.
- *A cache entry must never be reported valid while incomplete.* The
  file cache checks that the artifact is a loadable object, no older
  than the script, and that no tracked header has been edited since.

** Future Directions
:PROPERTIES:
:CUSTOM_ID: future-directions
:END:
Places where the architecture already has the shape for more than it
currently does. These are not commitments.

- *Backend selection from the CLI.* The interfaces exist and
  =CrispyScript= takes them as arguments, but =main.c= hardcodes the two
  concrete types. A =--compiler=clang= flag is a change to argument
  parsing, not to the design.
- *CRISPY_USE in the language server.* The compile flags the LSP
  generates come from =CRISPY_PARAMS= only, so a script that declares
  dependencies through =CRISPY_USE= alone is red in the editor and fine
  on the command line. The resolver the CLI uses is already a library
  type the server could call.
- *Header changes in watch mode.* =CrispyWatcher= monitors the script
  file, while the header tracker already knows the full dependency set
  from the depfile. Monitoring that set is a matter of wiring two
  existing pieces together.
- *Shared or remote caches.* =CrispyCacheProvider= was designed for this;
  what is missing is a portability story, since a cached artifact is
  valid only for the exact compiler and pkg-config output that produced
  it. The hash already includes both, so entries from different systems
  cannot collide -- they simply will not be reused.
- *More hook points.* =CRISPY_HOOK_POINT_COUNT= sizes the dispatch table,
  so adding a point is additive for the engine. It is not additive for
  plugins compiled against the old count, which is why the enum's tail
  is the place to add.
- *Introspection-driven bindings.* A GIR and typelib are already
  generated when =BUILD_GIR=1=; nothing consumes them yet, but the
  public API is annotated for it throughout.

** Thread Safety
:PROPERTIES:
:CUSTOM_ID: thread-safety
:END:
- =CrispyGccCompiler= and =CrispyFileCache= instances are safe to share across threads for read-only operations (get_version, get_base_flags, compute_hash, has_valid).
- Compilation and purge operations should be serialized if multiple threads share the same instances.
- =CrispyScript= instances should not be shared across threads. Create separate instances per thread.

** Building and Linking
:PROPERTIES:
:CUSTOM_ID: building-and-linking
:END:
To use libcrispy in your own project:

#+begin_src sh
# Get compiler flags
pkg-config --cflags crispy

# Get linker flags
pkg-config --libs crispy
#+end_src

Or in a Makefile:

#+begin_src makefile
CFLAGS += $(shell pkg-config --cflags crispy)
LDFLAGS += $(shell pkg-config --libs crispy)
#+end_src
